3. CONFIRMED FINDINGS: FORMAT 3, BOTH SIGNING MODES

Each attack test runs against encrypted archives with password access, with and
without owner signing. Attack transformations require neither the password nor
the signing key. Passwords are used only to create the legitimate fixture and
to act as the recipient opening the resulting archive.

A. Header reset bypass
Test: signature_audit_zero_sequence_header_can_hide_committed_content
An attacker zeros the selected header's root/sequence/auth/cleanup fields and
recomputes its public checksum. Password opening succeeds, a previously stored
variable is absent, and owner inspection reports unsigned.
Cause in main: lockbox.rs around 804/807 requires the authentication pointer and
checks the keyed header tag only when sequence > 0. The manipulated empty-state
fields skip verification and commit traversal.

B. Partial ciphertext replay
Test: signature_audit_old_variable_ciphertext_can_be_replayed_without_keys
Create VALUE=alpha, retain its encrypted variable page, then commit VALUE=bravo.
Copy the old page verbatim over the current variable-root location. Opening and
reading returns alpha. The signed case still reports a verified owner signature.
The attacker needs a prior ciphertext page/snapshot, not a decryption key.
This is partial state rollback inside the latest archive, not simply replacing
the entire archive with a complete older valid copy.
Cause in main: page AAD includes archive ID and page-supplied page ID/sequence,
but reads do not bind these to the expected location/current referenced version.
The encrypted archive's owner signature covers commit/root metadata, not a
recursive digest of the content graph.

C. Public access-directory metadata manipulation
Test: signature_audit_public_key_slot_ids_can_be_changed_without_keys
Change public key-slot IDs in both directory copies and recompute public page
checksums. Password opening succeeds and exposes the modified IDs; owner
verification still succeeds. IDs are used to identify slots for removal.
This proves unauthenticated slot metadata, not password recovery or decryption
by the attacker. Audit other access fields rather than assuming they share or
do not share this weakness.

D. Protections that did work
Test: signature_audit_ciphertext_bitflips_and_mode_downgrades_are_rejected
Encrypted commit-root/auth ciphertext bitflips reject. A signing-mode flag flip
with nonzero sequence and only public-checksum repair also rejects.

5. REQUIRED SECURITY DESIGN

Threat boundary:
  - An outsider may read, alter, reorder, truncate, splice, and replay archive
    bytes, including retained historical bytes, but lacks the password/content
    key and owner private signing key.
  - Password holders are authorized writers for unsigned password archives;
    they can replace contents and re-authenticate them. No individual authorship
    or resistance to malicious authorized writers is promised.
  - Whole-archive rollback to a previously valid complete snapshot cannot be
    detected by a purely self-contained archive without trusted external state.
    State this limit; do not confuse it with preventable partial replay.
  - Availability against arbitrary destruction of the entire file is not a
    cryptographic guarantee. Fail closed or perform explicitly reported recovery.

Authenticate archive interpretation in every accepted state, including an empty
archive. Do not allow an untrusted sequence, mode, missing pointer, fallback slot,
or recovery marker to turn off integrity checks. Empty state must be distinguishable
from a forged reset using keyed authentication or an equally strong construction.

Bind every accepted graph reference to the intended object/current version and
its bytes: data, TOC, variables, forms, manifests, allocation/free-space state,
and access metadata. Choose and document a construction compatible with the
v4 authenticated graph (e.g. authenticated child commitments, expected identities
and versions). Checking physical offset alone is insufficient when storage is
reused; checking a page's self-reported sequence alone is insufficient too.
Support authenticated selective/range reads and bounded resource use; do not
replace the security design with an unconditional whole-archive scan on every
read merely to pass these tests.

Authenticate access-directory metadata after unlocking. The credential bootstrap
may need public data, but public parseability must not imply trusted authority.
Bind relevant IDs, slot types, labels, key-wrapping parameters, restrictions,
membership/removal, generation, archive identity and directory copies to an
authenticated commitment. Preserve wrapped-key authentication and validate KDF
parameters/resource bounds before expensive work. Mirrors, backups, recovery and
credential-cache paths must not bypass the same checks.

Owner-signed modes retain an owner-authenticated commitment to the accepted state.
If a signature is presented as covering content, ensure graph commitments make
that claim true. Embedded-key validity alone does not establish sender identity;
do not add a new signer-pinning workflow for ordinary password sharing.

7. ACCEPTANCE GATES

Authentication:
  - All three accepted attacks above reject or enter an explicit, safe recovery
    flow. Never successfully report stale/empty/unauthenticated content as current.
  - Genuine new/empty archives remain usable; empty-to-nonempty/reopen transitions
    are covered. No sequence/mode/version/fallback combination bypasses validation.
  - Replay/reordering/splicing covered for files, variables, forms, tree levels,
    reused offsets, same/cross archive IDs, access-directory copies and generations.
  - Test with repaired public checksums, not only naive byte flips. Test partial
    snapshots, missing copies, malformed lengths and truncated tails.
  - Signed, unsigned, plaintext and encrypted modes retain explicitly documented
    guarantees. Plaintext unsigned cannot promise adversarial integrity; do not
    imply otherwise. Password-only protected modes do not require owner identity.

Lifecycle/recovery:
  - Public CLI sender and recipient use separate temporary Vault/session contexts.
    Password-only create/open/read/add/replace/remove/reopen and exact byte checks.
    Repeat/no-change operations, incorrect password, changed password, access
    add/remove/revoke, signed-mode refusals, and applicable safety paths.
  - Exercise corresponding native/binding/Dart and other supported language APIs,
    explicit read-only versus writable handles, and no implicit signer generation.
  - Crash/process-death and interrupted recovery do not resurrect removed state,
    trust unauthenticated ownership, or erase outside authenticated reservations.
  - Recovery, compaction and migration verify the resulting graph and data before
    replacement; preserve source/backup on interruption or failed validation.

Compatibility/release:
  - Current 0.4.x is format 3 and must remain bidirectionally interoperable.
    New incompatible commitments belong in the reserved 0.5.x/format-4 line.
    Do not claim security-layout changes are compatible from version numbers alone.
  - Verify actual CLI/binding versions within the selected line in both directions,
    persisted Vault compatibility, historical readers/migration paths, and packages.
  - Follow Rust AGENTS migration requirements for format changes. No production
    deployment/publication is authorized by this handoff.

Validation discipline:
  - Delegate tests/waits to a low-cost agent; do not repeatedly poll it.
  - Focused tests during implementation; broad integration checks at the completed
    security checkpoint. No full-suite reruns for each experiment/text-only change.
  - Formatting only at the commit stage using the tracked hook; preserve unrelated
    work and partially staged-file protections.
  - Do not weaken integrity or capacity constraints to obtain benchmark wins.
    Retain old benchmark results with their exact old guarantees; rebaseline the
