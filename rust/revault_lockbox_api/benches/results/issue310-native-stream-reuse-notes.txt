Issue #310: retain one verified native packed frame during stream_content
Base 446e5d1, 2026-09-22. Native feature only; no format or packing-target change.

stream_content now shares a native reader (verified metadata and index) and
zeroizing decoded bytes between adjacent slices of the same physical frame.
Each slice still validates its reference and manifest membership, and checks
source identity, padded extent and external failure latch before delivery.
The visitor borrows its slice without another allocation. Previous local state
is dropped before allocating another frame, and is wiped on return/error/unwind.
One operation-local frame is bounded by the native 4 MiB maximum; the existing
profile-controlled 64 MiB decoded cache remains separate. Existing decoded cache
entries are reused only after reopening metadata/index and matching their
identity and slice manifest. Interactive does not populate the persistent cache.
Single-file frames, sparse content and pending content retain the existing path.

Benchmark fixture option: REVAULT_ZIP_READ_CREATE_PROFILE=BulkImport (new,
optional); default stays Interactive. Reader profiles remain separate. Both
executables use the same benchmark code, built with native-block-layout.
Baseline temporarily used HEAD files.rs; restored before building candidate.
