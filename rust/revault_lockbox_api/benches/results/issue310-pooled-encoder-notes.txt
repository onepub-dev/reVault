Issue 310: reuse wiped compression workspace buffers across slice writes

Base 472f597; prior production source ff9716c. Retain this candidate based on
focused native protected-write improvements and correctness/cleanup coverage.
Only large single-worker in-memory slice writes use the new callback, in both
layouts. Streaming inputs and parallel preparation keep their existing codec.
This is not evidence of faster CLI or streamed writes.

A per-thread slot retains at most 8 MiB of zeroed scratch/output capacity.
Buffers are reused only for exact matching sizes. Encoder state is reconstructed
for each operation and reused for equal-sized compressible frames in that write.
Neither borrowed backing buffer grows. Full capacities are wiped before pooling
on success, error and unwinding; failed TLS access/reentry drops zeroizing owners.
An occupied pool is not replaced by a returning nested lease. TLS destruction
releases zeroizing buffers. This trades up to 8 MiB idle memory per participating
thread for allocation reuse; it is separate from archive page-cache budgets.
No measured peak-memory improvement is claimed. Level3/2MiB requires 2263369
scratch bytes plus 2105344 output bytes. Encoded output is copied to a compact
owned Vec and follows existing prepared-frame zeroization.

Eligibility requires explicit Zstd configuration, compressible initial frame,
64KiB through maximum frame size, levels below18, and combined required buffers
within the cap. Higher levels, incompressible frames, changed frame lengths,
workspace setup/encoding errors and oversized workspaces use existing encoding.
Levels18-22 retain their established numeric path because prior experiments
found different workspace bytes at level18. Format and dependencies unchanged;
no new unsafe code. Native v4 remains opt-in; no migration or activation here.
