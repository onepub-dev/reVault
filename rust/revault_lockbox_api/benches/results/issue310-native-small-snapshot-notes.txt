On a decoded-cache miss, a complete native frame whose logical and physical
lengths are each at most 16 KiB can be fetched in one bounded source read. The
same Reader validates header, protected metadata, committed descriptor, index,
manifest slice and data against a scoped memory snapshot. This is restricted to
file/external storage; an in-memory archive keeps its direct path. Partial-frame
ranges and larger frames retain their existing bounded readers.

Live source identity/extent and write revision are checked around the snapshot.
An external failure after the source read still prevents returning decoded bytes.
Both the snapshot and decoded error buffers are wiped. The scoped snapshot guard
also wipes on unwind. Cache insertion retains the original source revision and
verified frame reference, not the temporary memory source's revision.
No persistent format or public API changes. Native activation is unchanged.

Raw measurements: issue310-native-small-snapshot-paired.csv, 96 rows, identical
bench source in both binaries. Use the same interleaved three-run, five-sample
protocol documented in issue310-native-whole-cache-notes.txt: CASE=small,
MODE=plain, ACCESS=whole; both creation profiles, both corpora, both compression
settings and both read profiles. Each phase checks 480 MiB/122880 returned files
per implementation, with fresh archive handles and warm OS caches.

Medians of the three per-run medians:
- Interactive creation: 15.808-17.791 ms before, 7.661-9.583 ms after;
  individual speedups 1.84-2.06x. After/ZIP ratios 1.196-1.371.
- BulkImport controls: individual speedups 0.97-1.02x; after/ZIP 0.796-0.967.
  Small mixed control changes are not a formal non-regression result.
- Interactive whole-file reads still miss ZIP parity. These results do not
  establish read-handle, range, large-file, protected-mode, write, or cold-OS-cache
  performance. Those gates and the remaining recovery work are still required.
