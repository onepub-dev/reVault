Correction to the preceding investigation: the numeric convenience slice API
has no caller output parameter, but the pinned zstd-complete 0.2.0 also exports
StaticEncoderWorkspace. It accepts caller-backed scratch and output slices and
promises output capacity checks prevent growth. No dependency fork is necessary
to investigate reusable output storage. The earlier one-line smaller-allocation
prototype still lacks the secure growth proof required for production use.

This candidate scoped TLS-owned ZeroizingBytes scratch and output buffers to
one large, single-worker, in-memory file write. Explicit numeric compression
used StaticEncoderWorkspace with parameters derived for each exact input length;
finished bytes were copied into compact return Vecs. Frame output/scratch storage
was reused within that write and fully wiped on scope completion/error/unwind.
Growth replaced the entire zeroizing owner rather than reallocating live data.
Scratch limit 32 MiB; inputs 64 KiB through 4 MiB. Out-of-scope/unsupported cases
fell back to the existing numeric encoder. Encoder state itself was reconstructed
on every frame: this experiment did NOT reuse the complete initialized encoder.
Readers, parallel import and streaming input were not changed.

Reject this candidate rather than retain new lifetime/complexity costs without
an established performance gain. The earlier smaller-allocation result does not
transfer automatically to this different approach. Construction and zeroing of
scratch, compact output copies and per-frame encoder reconstruction remain possible
costs; this experiment does not separately measure or prove their contribution.
Next candidate can investigate keeping a caller-backed initialized encoder alive
across equal-sized frames with explicit lifetimes and scope-bound zeroizing owners,
retaining the ordinary path for parameter changes/partial final frames. That is
not implemented here. Production read/write gates and known recovery/release
requirements remain open; native stays opt-in.
