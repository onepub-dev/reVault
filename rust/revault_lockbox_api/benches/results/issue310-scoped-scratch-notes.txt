Issue #310: bounded scratch reuse for large compressed content streams
====================================================================
Base fb6c61f, 2026-09-22. Both existing and experimental native layouts.

The allocation-sensitive compressed slowdown motivated a read-operation-local
scratch arena. stream_content selects reuse when at least 8 MiB of compressed
file slices use frames of at least 64 KiB. Counting slices rather than shared
frame sizes avoids activating a large workspace for many tiny cached files.
Small and raw streams retain the existing decoder path. The eligibility walk
stops as soon as it reaches the threshold.

The thread-local slot locates scratch only within a synchronous stream call;
it is cleared at the outermost call's end, not retained between operations.
Nested streams share the allocation. ZeroizingBytes wipes its full capacity on
success, error and panic unwind. Growth replaces the wrapper, wiping the old
buffer before freeing it instead of reallocating unwiped history. No unsafe
code, new dependency, decoded-output cache or persistent plaintext cache added.

StaticDecoderWorkspace reconstructs decoder state per frame but reuses its
caller-owned allocation. The current output length and advertised Zstd window
size the allocation, bounded to a 4 MiB history plus codec tables. Header parsing
here is only a sizing hint; the decoder still validates the complete header.
Skippable prefixes, oversized output/history, and later concatenated frames
that exceed the workspace bound fall back to the original decoder. Existing
format acceptance, byte-length checks, block/index integrity, source validation
and signed-content verification remain. Archive bytes and write codec unchanged.

Why not always allocate the maximum?
The first fixed-4-MiB-window prototype improved the full native 64 MiB benchmark
sequence dramatically but slowed the existing-layout 1 MiB case. Frame-sized
allocation alone reduced, but did not consistently remove, that small penalty.
The final amortization threshold preserves the small-stream path. Raw data from
all three phases is retained; rejected small-case regressions are not discarded.

Measurement method
------------------
rustc 1.88.0 optimized bench, CPU 2, warm OS caches, fresh archive handle for
every sample, default padding, four patterned files. ZIP uses Rust stored or
deflate, lockbox raw or default Zstd. Returned bytes are compared exactly for
every full/range/stream read. Total timings include open, verification and drop,
including scratch wipe. No build/test overlaps timing. Background load varies.
No process-wide allocator overrides in any measurement in this report.

Common command:
  REVAULT_ZIP_READ_CASE=large REVAULT_ZIP_READ_MODE=plain
  REVAULT_ZIP_READ_SIZE=67108864|1048576 REVAULT_ZIP_READ_SAMPLES=5|15
  taskset -c 2 EXE
The isolated-fixed phase additionally selects COMPRESSION=true,
PROFILE=Interactive and ACCESS=stream and uses nine samples.
The raw CSV prefixes every source row with phase, variant and run. Values remain
process medians, not individual sample distributions or confidence intervals.

Results and limits
------------------
The initial fixed-workspace full-matrix ABBA showed native 64 MiB compressed
Interactive streaming 334.718 / 369.730 ms before versus 107.146 / 133.395 ms
after. The isolated case was mixed (before 159.844 / 131.283; after 158.489 /
121.483), consistent with the preceding allocator-state diagnosis.

The final frame-sized, thresholded implementation measured native 64 MiB
streaming 102.616 ms Interactive and 101.748 ms ReadMostly. Paired ZIP was
58.558 / 58.247 ms: native remains about 1.75x ZIP, NOT parity.
Final existing-layout 64 MiB streaming: Interactive 137.349 -> 98.789 ms and
ReadMostly 166.862 -> 126.915 ms. ZIP/background variation is visible; these
are descriptive observations, not formal regression-gate confidence bounds.
Final existing 1 MiB streaming: Interactive 1.744 -> 1.719 ms, ReadMostly
2.002 -> 1.932 ms, with the workspace bypassed for this four-file workload.
Archive lengths match their baseline for each layout and compression setting.
Later random/range cases also change because prior streaming changes allocator
state. Their direct reader implementation was NOT optimized in this checkpoint.

Adjacent final-implementation repeat (full matrix, five samples per row) confirms
the improvement: native Interactive compressed streaming 315.875 -> 102.194 ms,
ReadMostly 315.247 -> 101.806 ms. ZIP Interactive was 58.961 -> 58.235 ms and
ReadMostly 59.547 -> 58.573 ms. These rows are tagged final-native-repeat.

Follow-up: thread-local teardown compatibility
---------------------------------------------
Review of ee23a7b identified a new panic when another thread-local destructor
called the decoder after the scratch slot had already been destroyed. A test
initializes that destructor before scratch, catches its panic internally to
avoid aborting the test process, and checks the recovered bytes. It failed on
ee23a7b with AccessError, proving a real compatibility regression.

Scope setup, cleanup and decode now use try_with. If the slot is unavailable,
scope setup does not claim ownership and decoding uses the original decoder.
Normal scoped reuse, memory wiping and all codec checks remain in place.
Four focused workspace tests pass; the public nine-MiB streaming lifecycle
passes in both layouts; native/external-source library/tests strict Clippy
passes. No new performance measurement or speedup is claimed for this fix.
