Security/retention decision: do not retain this one-line prototype as production.
Smaller initial capacity can introduce buffer growth that releases previous
allocations before ZeroizingBytes sees the final Vec. Current cleanup of the
returned allocation does not prove historical reallocations were wiped.
Separately, the codec emits trial compressed blocks and truncates rejected output
in c_port/block_emit.rs, so final length is not a valid bound on previously
initialized bytes. Shrinking or skipping spare wiping without tracking that
history would be unjustified. No third-party source or allocation policy change
was made outside the temporary target copy, and no dependency upgrade is claimed.

The measured gain justifies investigating a secure codec output API: caller-owned
or reusable storage with explicit handling of every growth, truncation and drop,
or a bounded encoder that avoids releasing written buffers during growth. A
production solution needs exact-output/round-trip coverage across compressible,
incompressible and mixed blocks plus cleanup tests on rejection/reallocation,
then full read/write performance gates. This diagnostic does not provide those
security proofs. No additional correctness-suite result is claimed.
Native remains opt-in; read parity, write gates, signed recovery and release work
remain incomplete. Nothing pushed or published.
