Resolved here: packed native survivor missing from signed recovery after a
stale page is appended. First failing combination: unencrypted, signed, raw,
default padding. Normal open correctly rejects extra bytes outside a sealed
publication. Recovery had reused that open without bounding its private copy,
therefore it could not establish owner authorization for an intact survivor.

Recovery now trims only its private authentication copy to header.sealed_len.
It refuses lengths below the header or beyond available bytes, and performs
normal header-tag, commit-chain, owner-signature and content authentication.
The normal open contract and original source bytes are unchanged. No codec,
write behavior, archive format or performance improvement is claimed here.

Focused regression passes all 16 encryption/signing/compression/padding cases.
It verifies survivor bytes after recovery/salvage and deleted-file absence.
New negative cases forge the sealed length in both slots and repair only the
unkeyed checksum, leaving metadata authentication invalid: below-header,
extended-to-trailing-data and beyond-available lengths all refuse signed native
salvage. This fixture mutation has no public CLI equivalent and is unit-only.

Decoder investigation (no dependency change): the pinned released
zstd-complete 0.2.0 DecodeBuffer hashes drained output whenever its hash feature
is enabled, regardless of the frame content-checksum flag. FrameDecoder exposes
that result through get_calculated_checksum; DecoderWorkspace delegates to the
same decoder. Removing hashing is not an available per-frame reVault setting
and would require deliberate upstream API design/validation. The user's dirty
zstd checkout was not modified. This is not evidence of a retained speedup.
