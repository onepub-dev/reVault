Local dependency source inspection: zstd-complete 0.2.0 numeric slice API
compress_slice_c_level delegates to encode_frame_no_dict. The dfast frame
encoder allocates output with Vec::with_capacity(compress_bound(src.len())).
That output Vec is returned with its capacity intact. The current public numeric
slice API does not accept caller-provided output storage. Switching to the
Read/Write numeric wrapper still allocates the full encoded Vec internally and
also stages input, so it does not solve this allocation behavior.

A next candidate should reduce codec output allocation at its source or reuse
storage without weakening wiping. Merely shrinking the Vec before ZeroizingBytes
destruction could release unwiped spare bytes; it is not a justified fix.
Skipping spare wiping based on the final compressed length is also not justified:
the returned length alone does not prove which bytes were previously initialized.
Changing compression algorithms/levels would need its own size/speed tradeoff
evaluation and is not required to investigate this allocation issue.
