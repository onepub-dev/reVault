Issue 310: reject earlier compressed-buffer release in native writes

Base b6d6b30, production source ff9716c. Candidate is fully reverted.
The native writer seals a page into its own immutable zeroizing allocation,
then stages/prepares/flushes the page and publishes chunk references. Its input
PreparedCompressionFrame.stored otherwise remains alive until function exit.
Prototype explicitly dropped that ZeroizingBytes immediately after successful
page encoding, before sequence allocation, preparation/storage I/O and reference
publication. Same full-capacity wipe, earlier in the operation; no skipped
cleanup, changed page bytes or dependency changes. Failure before sealing kept
normal RAII cleanup. Remaining prepared fields were moved normally afterwards.
Page-write telemetry would include cleanup in this prototype; total benchmark
time is the metric used below, not an apparent change in per-stage attribution.

Rationale/hypothesis: the codec's oversized allocation could be released before
preparation allocations and storage work, potentially reducing allocation
pressure. No allocation/peak-memory measurement was performed, so no memory
improvement or allocator-causation claim is made.

Validation before timings:
- staged_native_pages_use_preparation_and_abort_append_and_reused_extents passed
  with native-block-layout,external-source.
- all-targets Clippy with those features and -D warnings passed.
- Full suites were not repeated for this rejected candidate. Production files
  restored exactly from HEAD; prior complete suite results remain in the
  shared-window notes.
