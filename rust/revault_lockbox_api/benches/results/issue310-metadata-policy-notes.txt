Native page metadata previously attempted compression independently of whether
it could reduce the padded allocation. With compression enabled and padding on,
compute the smallest possible allocation for the header, codec/length prefix,
protection overhead and data packet, allowing a hypothetical empty compressed
metadata stream. If raw metadata fits that same allocation, compression cannot
save physical space: emit the already-supported uncompressed metadata codec.
Otherwise retain the previous codec selection. Do not do the sizing calculation
for compression-disabled or unpadded pages. Data compression is unchanged.

The rule is conservative: it skips codec work only when space savings are
impossible, without first spending CPU on a compressed candidate. It does not
introduce a format, codec or API change. Existing metadata authentication,
committed index/data verification, padding, and decoding paths remain intact.

The new codec test covers encryption, signing and both padding choices with a
single-file and a 128-slice manifest. It recompresses identical logical metadata
using the former selection rule, asserts identical physical page size, verifies
uncompressed metadata only in the proven no-saving case, preserves compression
when it saves space and for unpadded pages, and decodes exact file bytes.

Final measurement files:

- issue310-metadata-policy-writes.csv: 192 creation/add/commit/close rows.
- issue310-metadata-policy-write-controls.csv: 480 additional write control rows.
All rows were collected after the final successful release build. Both binaries

Main protocol: CASE=small, ACCESS=whole, SAMPLES=5, WRITE_PROFILE=1; iterate MODE
plain/encrypted/signed/encrypted-signed, CREATE_PROFILE Interactive/BulkImport,
CORPUS pattern/random. Leave PROFILE and COMPRESSION unset to cover both values.
Use the REVAULT_ZIP_READ_ prefix for these environment names. Repeat three times;
run before then after within each case, reversing phase order on the second run.
Prepend phase/create_profile/run to read CSV and phase/run to write CSV. Each phase
byte-verifies 491520 file results (1920 MiB) per implementation via fresh archive
handles; OS caches are warm. File count is 512, bytes per file 4096.

Controls: twenty alternating before/after pairs, MODE signed/encrypted-signed,
CORPUS pattern/random, and the three unchanged policy families:
Interactive + compression=false, BulkImport + compression=false/true.
PROFILE=Interactive, SAMPLES=1, other settings as above. Each of 480 fixtures is
reopened and every file byte checked by both implementations (960 MiB each).
This addresses variability visible in signature-heavy three-run write samples;
it is not evidence for all write workloads or a formal non-regression gate.

Medians of the three per-run medians in the main matrix:
- Plain Interactive compressed reads: 1.157-1.183x faster; writes 1.185-1.216x.
  After/ZIP read ratios: 0.954-0.993.
- Plain Interactive uncompressed after/ZIP: 0.977-0.999; plain BulkImport across
  compression settings: 0.791-0.967. This small whole-file workload approaches
  parity in plain mode, but does not show a 10% lead in every case.
- Protected Interactive compressed read speedups: 1.066-1.173x; write speedups:
  1.121-1.161x. These are comparisons with the previous lockbox binary, not a
  claim that protected archives match unprotected ZIP performance.
- Expanded unchanged signed-write control speedups: 0.963-1.022x. Large apparent
  slowdowns in some three-run cells did not persist in the larger control set;
  smaller mixed timing changes remain and must not be hidden.
