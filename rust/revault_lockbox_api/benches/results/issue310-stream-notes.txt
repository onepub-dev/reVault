Issue310: reuse wiped encoder buffers for sequential streamed imports

Base d7dd0d0; slice pooling production62180a3. Retain streamed integration based
on measured protected compressed-write gains and lifecycle/cleanup coverage.
Sequential reader imports now use the same per-operation encoder and bounded
per-thread wiped buffers as large slice writes. EncoderFrame carries only length
and an incompressibility decision, so the caller can refill its original buffer
without a first-frame copy or a retained input borrow. Pipeline eligibility
avoids probes for raw configuration and high levels; final short-frame guard
also avoids probing inputs outside workspace size eligibility.
Initial and subsequent host-read accounting remains; a genuinely empty stream
still emits its existing empty frame. Reader errors unwind the writer and codec
lease. The reusable input buffer now has a ZeroizingBytes owner, wiping its full
capacity on success and failure. Frame state, output selection, small-tail
fallback, level18-22 fallback, pool8MiB retention limit and cleanup are unchanged.
Parallel worker imports remain on their existing path. No format/dependency or
public API change. Native layout stays opt-in.

Bench protection_gate accepts REVAULT_GATE_STREAM_INPUT=1 for public
add_file_from_reader via Cursor instead of add_file. Flag is inherited by child
comparisons and independent persisted verification remains unchanged. This
measures streaming API overhead over memory-backed input, not filesystem read
latency or complete CLI throughput. CPU2 affinity makes Auto available
parallelism one; the tested path is sequential. Ordinary multi-core Auto may
still choose the unchanged parallel path. Do not extrapolate these gains there.
